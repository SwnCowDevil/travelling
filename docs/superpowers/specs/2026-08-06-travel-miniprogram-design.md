## 2. 产品目标

本项目是个人自用的国内旅行推荐与足迹管理微信小程序。第一版解决三个核心问题：

1. 根据出发地、月份或具体日期、距离和个人偏好，一键获得三个可靠的国内旅行推荐。
2. 查看目的地的推荐理由、交通、天气或历史气候、行李清单、注意事项和简要攻略。
3. 管理想去、去过、想再去和不想去的地点与行政区，并在中国地图上形成个人旅行足迹。

第一版以可靠、可解释和可降级为原则。AI 不直接决定全部结果，也不能突破距离、月份和明确排除项等硬约束。

## 3. 第一版范围

### 3.1 包含

- 微信静默登录，以 `openid` 隔离用户数据。
- 微信头像、昵称或默认头像与默认信息。
- 约 150 个精选国内目的地的结构化基础库。
- 当前定位与手动选择地址两种出发地方式。
- 月份必选，具体日期范围可选。
- 距离、排序、淡旺季、人流、人文、景色、分类、天数、预算、交通偏好和同行类型筛选。
- 规则筛选与评分、AI 重排、推荐理由和按需攻略。
- 每次三个推荐、换一批和近期推荐历史。
- 全国、省、市/区县地图下钻及状态点亮。
- 具体目的地和行政区分别标记。
- 到访日期、备注与去过次数统计。
- 系统默认 AI 配置和用户个人 AI 配置。
- Open-Meteo 实时预报与历史天气数据接入。
- SQLite 持久化和定时备份。

### 3.2 不包含

- 照片游记和完整旅行日志。
- 旅行伙伴、消息通知和社交功能。
- 自动购票、酒店预订和完整路线规划。
- 独立运营管理后台。
- 离线双向同步。
- 多实例、高并发和高可用数据库部署。

未实现功能不在菜单中展示空入口。

## 4. 信息架构

底部使用三个一级页签。

### 4.1 推荐

- 出发地与定位切换。
- 月份、可选日期和距离范围。
- 常用偏好快捷筛选。
- 更多筛选底部抽屉。
- 一键推荐与换一批。
- 三张推荐卡片。
- 近期推荐历史入口。

### 4.2 旅行地图

- 全国、省、市/区县逐级浏览。
- 查看、想去、去过、想再去、不想去五种地图模式。
- 行政区直接标记。
- 目的地聚合点亮。
- 分类清单、地点搜索和状态管理。
- 到访记录入口。

### 4.3 我的

- 微信头像、昵称或默认信息。
- 去过次数、去过地点、想去、想再去和不想去统计。
- AI 配置与 Token 管理。
- 定位、缓存和减少动态效果等通用设置。
- 关于、数据来源与免责声明。

地点清单统一在旅行地图页管理，避免与“我的”重复。

## 5. 推荐筛选与排序

### 5.1 筛选项

- 出发地：当前位置或手动选择地址。
- 时间：月份必选，日期范围可选；默认当前月。
- 距离：50、200、500、1000、2000 公里及不限。
- 距离排序：综合推荐、由近到远、由远到近。
- 季节：淡季、旺季。
- 人流：偏好人少、可接受人多。
- 内容偏好：人文、景色。
- 分类：海岛、古城、山川、草原、城市、沙漠及可扩展分类。
- 可用天数。
- 人均预算。
- 交通偏好：自驾、高铁、飞机。
- 同行类型：独自、情侣、亲子、朋友、老人。
- 包含去过：默认关闭。

除月份外，其余筛选均可不选。不选择表示不限制或不加权。

### 5.2 硬约束

后端先排除：

- 超出距离范围的目的地。
- 用户标记为“不想去”的目的地。
- 默认状态下已“去过”且未标记“想再去”的目的地。
- 与所选月份明显不适宜或季节性关闭的目的地。
- 不满足用户明确设置的天数和预算上限的目的地。

“想再去”允许参与推荐。“包含去过”开启后，普通去过地点也允许参与。

距离以出发地和目的地坐标之间的直线距离计算，并在界面明确标注。交通路线距离和预计时间仅作详情建议，不参与距离硬筛选。

### 5.3 基础评分

初始综合评分权重：

- 月份与气候适配度：30%。
- 用户偏好匹配度：25%。
- 距离与交通适配度：15%。
- 天数和预算适配度：15%。
- 人流及淡旺季偏好：10%。
- 目的地基础质量：5%。

选择由近到远或由远到近时，距离成为主排序键，综合评分作为次排序键。权重放在后端配置中，后续可调整。

“最推荐”是默认综合排序结果，不再作为普通开关。

### 5.4 AI 重排

规则引擎将高分候选及用户条件发送给 AI。AI 只能在候选集合内重排，不得引入未入库地点。返回结果必须通过后端结构校验，至少包含：

- 三个目的地 ID。
- 每个目的地的简短推荐理由。
- 条件匹配亮点。
- 需要注意的不匹配项。

AI 返回无效 JSON、未知目的地、超时或错误时，后端直接使用规则评分结果。

### 5.5 换一批与历史

- 每次展示三个目的地。
- 换一批沿用当前筛选条件。
- 同一推荐会话内，已展示地点暂时排除；候选不足时允许低优先级重复并明确提示。
- 推荐历史保存条件、结果、时间和数据版本。

## 6. 目的地详情与攻略

推荐卡只展示地点、匹配分、直线距离、季节、人流、简短理由和状态操作。

打开详情时按需生成并缓存：

- 为什么推荐及不完全匹配项。
- 建议天数和人均预算。
- 推荐交通方式与预计用时说明。
- 实时天气或历史气候。
- 行李清单。
- 注意事项。
- 推荐玩法。
- 简要分日行程。
- 数据来源、更新时间和 AI 内容免责声明。

攻略缓存键由目的地、月份或日期、出发地区域、关键偏好和数据版本组成。基础目的地资料更新时，旧缓存失效。

## 7. 天气设计

默认使用 Open-Meteo，由 FastAPI 统一调用；小程序不直接请求第三方天气接口。

- 日期位于预报范围内：展示逐日天气、温度、降水和风力等实时预报。
- 日期超出预报范围或只选择月份：使用多年历史数据计算常见温度区间、降雨特征和穿衣建议。
- 页面必须标注“实时预报”或“历史气候参考”。
- Open-Meteo 不可用时，回退目的地库中的基础气候信息。
- 保留天气供应商适配器，后续可配置其他服务地址和密钥。

Open-Meteo 的免密钥访问仅用于符合其非商业使用条款的个人项目；若项目转为公开商业运营，需要重新评估授权与服务等级。

## 8. 足迹、状态与地图

### 8.1 具体目的地状态

一个目的地最多有一个当前状态：

- 想去。
- 去过。
- 想再去。
- 不想去。
- 无状态。

“想再去”要求至少存在一条到访记录。收藏作为独立布尔属性预留，但第一版不提供独立收藏入口。

### 8.2 到访记录

每条记录包含用户、目的地、到访日期、可选备注、创建时间和更新时间。

- 标记去过时创建到访记录。
- 同一天同一地点重复添加时提示，用户确认后仍可添加。
- 去过次数从有效记录实时统计，不维护独立计数字段。
- 支持补录、修改和删除。
- 删除最后一条到访记录时，如果状态是“想再去”，必须选择改为“想去”或无状态。

### 8.3 行政区状态与聚合

省、市和区县可直接设置状态。行政区直接状态和目的地状态分别保存。

- 标记“去过四川”不等于去过四川全部目的地。
- 去过稻城亚丁会使所属区县、市和省产生聚合点亮。
- 地图详情需区分“用户直接标记”和“由下属目的地聚合”。
- 行政区去过次数为下属目的地到访记录数。
- 只有行政区直接标记而没有具体记录时，显示“已标记去过，暂无详细记录”。

### 8.4 地图交互

- 全国地图下钻到省，再查看市/区县。
- 查看模式点击区域打开底部详情面板。
- 标记模式点击区域先预览变更，再确认保存。
- 状态颜色：想去为绿色、去过为蓝色、想再去为橙色、不想去为灰色。
- 同一区域存在多类状态时，按当前查看分类着色，不使用单一颜色覆盖全部含义。
- 地图加载失败时显示行政区列表和状态清单，足迹仍可管理。

## 9. 页面布局与动效

### 9.1 推荐页调整

现有原型的五列顶部下拉在手机宽度下过于拥挤，改为三级筛选：

1. 核心条件卡：出发地、月份、日期和距离。
2. 横向快捷标签：淡旺季、人流、人文和景色。
3. `van-popup` 底部抽屉：天数、预算、交通、同行和分类。

### 9.2 详情页调整

内容使用分区卡片或折叠面板。默认展开“为什么推荐”和“注意事项”，其他模块按需展开，降低首屏信息密度。底部保留地点状态操作栏。

### 9.3 地图页调整

地图占主视觉区域，下方为可拖动底部面板。分类状态使用横向分段控件，避免把所有状态列表同时堆叠在地图下方。

### 9.4 动效

- 推荐加载依次显示“正在筛选目的地”“正在匹配偏好”“正在整理推荐”，同时展示三张骨架卡。
- AI 详情按模块独立加载，已完成模块先展示。
- 推荐卡以 150–250ms 淡入上移方式依次出现。
- 地图点亮使用一次颜色渐变和轻微扩散反馈。
- 状态操作使用按钮回弹、图标变化、轻触震动和 Toast。
- 不使用持续漂浮、循环渐变等耗电且干扰阅读的动画。
- 用户启用减少动态效果或设备性能较弱时，关闭非必要动画。

## 10. 技术架构

### 10.1 微信小程序

使用微信原生框架和 Vant Weapp。建议结构：

- `pages/recommend`
- `pages/destination-detail`
- `pages/map`
- `pages/visit-records`
- `pages/me`
- `pages/ai-settings`
- `components/filter-bar`
- `components/recommend-card`
- `components/status-actions`
- `components/weather-panel`
- `components/loading-stage`
- `services/auth`
- `services/api`
- `services/location`
- `services/cache`

小程序只调用自有 FastAPI，不保存系统默认 Token，也不直接调用 AI 或天气服务。

### 10.2 FastAPI

后端按职责拆分：

- 认证与会话。
- 用户资料和设置。
- 目的地与行政区。
- 推荐筛选、评分和 AI 重排。
- 攻略生成与缓存。
- 足迹、状态和到访记录。
- 地图聚合。
- 天气适配器。
- AI 供应商适配器与配置。

AI 请求使用异步 HTTP 调用，单次调用默认在 15–20 秒内超时。第一版不引入任务队列或 Redis。

### 10.3 数据库

第一版使用 SQLite：

- 启用 WAL 模式。
- FastAPI 初期使用单应用进程，避免多进程并发写入问题。
- 数据库文件路径通过环境变量配置。
- 每日生成一致性备份，并保留多个历史版本。
- 使用 SQLAlchemy 2.x 和 Alembic。
- 避免 SQLite 专属业务 SQL，为未来迁移 MySQL 或 PostgreSQL 保留空间。

当出现多用户、高并发、多后端实例或更高可用性要求时，再迁移服务型数据库。

## 11. AI 配置与安全

### 11.1 配置模式

“我的 → AI 设置”提供：

- 使用系统默认配置。
- 使用个人配置。
- 简单模式：只填写 Token。
- 高级模式：服务地址、模型 ID、接口协议、超时和分组备注。
- 测试连接。
- 恢复系统默认配置。

PackyAPI 默认采用 OpenAI 兼容端点 `https://www.packyapi.com/v1`。模型 ID 不写死，由服务端环境变量或个人配置提供。Token 分组只作备注；实际权限由 Token 在供应商侧的分组决定。

后端为不同协议定义适配器，首个适配器支持 OpenAI 兼容的 Chat Completions；后续需要 Responses API 或其他协议时新增适配器，不改变推荐业务接口。

### 11.2 Token 安全

- 系统默认 Token 只存在服务端环境变量。
- 用户 Token 使用服务端主密钥进行认证加密后入库。
- 客户端查询只返回掩码和末尾几位，不返回明文。
- 新配置测试成功后才替换旧配置。
- 删除个人配置后回退系统默认配置。
- Token 不进入日志、错误响应、推荐历史或缓存键。
- 默认仅允许 HTTPS 服务地址。
- 生产环境主密钥不与数据库备份存放在同一位置。

用户此前在对话中发送的 Token 不写入文档、代码、测试数据或版本库，正式开发前应在供应商控制台撤销并重新生成。

### 11.3 微信登录

- 小程序通过 `wx.login` 获取临时代码。
- FastAPI 使用 AppID 和 AppSecret 向微信换取 `openid` 与会话信息。
- AppSecret 只保存在服务端环境变量。
- 后端签发自己的短期访问令牌，不向小程序返回微信会话密钥。
- 头像和昵称仅在用户主动选择或授权后保存，否则使用默认信息。

## 12. 核心数据模型

- `User`：微信标识、昵称、头像、默认出发地和设置。
- `Destination`：稳定编码、名称、简介、坐标、行政区、分类、适宜月份、淡旺季、人流、气候、预算、天数、交通和质量分。
- `AdministrativeRegion`：行政区代码、名称、层级和父级关系。
- `DestinationStatus`：用户、目的地和当前状态。
- `RegionStatus`：用户、行政区和直接设置的状态。
- `VisitRecord`：用户、目的地、到访日期和备注。
- `RecommendationSession`：筛选条件、候选、最终结果、已展示集合、时间和数据版本。
- `GuideCache`：条件摘要、结构化攻略、模型、来源和有效期。
- `AIProfile`：配置模式、地址、模型、协议、超时、分组备注、加密 Token 和连接状态。

所有业务关联使用内部 ID 或稳定编码，不以可变名称作为外键。

## 13. API 边界

- `POST /auth/wechat`：微信登录。
- `GET/PATCH /users/me`：用户资料和设置。
- `GET /destinations`：目的地查询和搜索。
- `GET /destinations/{id}`：基础详情。
- `POST /recommendations`：创建推荐。
- `POST /recommendations/{id}/next`：换一批。
- `GET /recommendations/history`：推荐历史。
- `GET/POST /guides/{destination_id}`：读取或生成攻略。
- `GET /weather/{destination_id}`：天气或历史气候。
- `PUT/DELETE /destination-statuses/{destination_id}`：目的地状态。
- `PUT/DELETE /region-statuses/{region_code}`：行政区直接状态。
- `GET/POST/PATCH/DELETE /visit-records`：到访记录管理。
- `GET /map/summary`：地图层级聚合数据。
- `GET/PUT/DELETE /ai-profile`：个人 AI 配置。
- `POST /ai-profile/test`：测试连接。

接口统一返回业务错误码、用户可读消息和请求追踪 ID。状态修改和记录新增支持幂等键。

## 14. 业务一致性规则

- 新增第一条到访记录时，目的地状态自动设为“去过”。
- 后续新增记录只增加统计，不覆盖“想再去”。
- “想再去”必须至少存在一条到访记录。
- 删除最后一条记录且状态为“想再去”时，操作必须同时提交新的有效状态。
- “不想去”不删除历史记录，但保存前提示语义冲突。
- 地点或行政区状态变化后，地图聚合与个人统计从数据库重新计算或使对应缓存失效。
- 攻略缓存与目的地数据版本绑定。

## 15. 错误处理与降级

- 定位拒绝：引导手动选择，记住最近出发地。
- AI 超时、余额不足或格式错误：返回规则结果。
- 个人 Token 失效：回退系统默认；无默认时引导配置。
- 天气失败：回退历史气候或本地基础气候。
- 地图失败：回退行政区列表。
- 网络中断：保留当前筛选和已加载内容，提供手动重试。
- 候选不足三个：保持硬约束，放宽软偏好并说明原因。
- 数据冲突：以后端最新版本为准，前端刷新并提示。

## 16. 部署路径

### 16.1 开发阶段

- 本地运行 FastAPI。
- 使用 SQLite 文件。
- 微信开发者工具调试。
- 配置通过 `.env` 注入，`.env` 不进入版本库。

### 16.2 真机联调与上线

- 准备域名和一台入门级 Linux 云服务器。
- 若使用中国大陆服务器，完成域名 ICP 备案。
- 使用 Caddy 或 Nginx 提供 HTTPS，并反向代理 FastAPI。
- 在微信小程序后台配置 HTTPS request 合法域名。
- 使用系统服务管理 FastAPI 进程和自动重启。
- 每日自动备份 SQLite，并定期验证恢复流程。

Docker 不是第一版的使用门槛。后续需要标准化迁移时再补充 Docker 部署文件。

## 17. 测试策略

### 17.1 后端

- 硬筛选和距离计算。

## 18. 第一版验收标准

- 用户可以通过微信登录进入小程序。
- 只使用默认月份也能获得三个推荐。
- 距离、月份和不想去等硬条件不会被 AI 突破。
- AI 不可用时仍能返回基础推荐。
- 详情包含交通、天气或气候、行李、注意事项和攻略。
- 目的地和行政区都能设置四类状态。
- 到访日期可补录、修改和删除，次数统计正确。
- 地图能按状态查看，并区分直接标记与聚合点亮。
- 用户可以选择系统 AI 配置或安全保存个人配置。
- 天气服务无需用户提供 Key 即可运行，并有本地降级。
- SQLite 数据在服务重启后不丢失，备份可以恢复。
- 页面延续现有视觉语言，关键加载和状态操作有清晰且克制的动效。
- 小程序代码和版本库中不存在任何服务密钥。
